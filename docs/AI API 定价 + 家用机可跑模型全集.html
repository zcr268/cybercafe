零、网吧机器赚钱效率评估（针对 A001-10-003 及同型机）

目标机硬件：RTX 4080 SUPER 16GB 显存 / 31.2GB 系统内存 / 云网吧 swnetboot + COW 快照机（重启丢失本地数据）。
本章数据来源分两类：标 实测 者取自本仓库真机证据（docs/h3-16gb-config-feasibility.md、docs/qwen27b-feasibility.md、minimax-h3/README.md）；标 推算 者由公开市场价与产能估算，未经真机验证。驱动视为已就绪，不作为约束。

一句话结论：这台机器的最高效赚钱方式是「GPU 跑图像生成 + CPU 同时跑 OCR」双线并行；视频生成是陷阱（16GB 显存下产能太低，商用不成立）；LLM 聊天零售无竞争力（被大厂价格战碾平）。

硬件层面的三个硬结论：
① 16GB 显存是分水岭——它刚好够「生产级图像生成」，但不够「商用级视频生成」（720P 需更高量化档 + 更大激活，16GB 装不下）。
② 31.2GB 内存是隐藏瓶颈——H3 需约 27GB 参数驻留，只剩约 4GB 给系统。这意味着跑视频时这台机器几乎不能再干别的，而跑图像/OCR 时内存很宽裕。
③ COW 非持久磁盘放大了视频的劣势——每次重启要重拉 27GB 权重，而它的产出又最低。

为什么视频生成是陷阱（硬件层面的论证）：
真机实测 实测：H3 在 16GB 卡上 102.65 秒生成 25 帧（640×384，UD-Q2_K_XL 最低档，峰值显存约 9GB）。25 帧 @24fps = 1.04 秒视频，即约 99 秒墙钟换 1 秒视频。
· 640×384 无法商用（客户要 720P 起）；
· 商用 720P 需提高量化档与分辨率，耗时按 4–8 倍估算 → 每小时仅产 5–9 秒；
· 按市场价 0.6 元/秒，每小时收入 3–5.4 元；
· 网吧机位的机会成本约 5–15 元/小时 → 接单即亏本。
· 更致命的是内存：跑 H3 时 27GB 参数占满 31.2GB 内存，这台机器连 OCR 都并行不了，等于放弃了最高效的那条线。
唯一可行用法：只做自有内容（网吧宣传片、客户个性化短视频），不对外按秒接单。
为什么 LLM 聊天不能零售：大厂 API 已打到 1–2 元/百万 token。这台机器 27B 模型跑 27–30 tok/s，一小时产出约 10 万 token（0.1 百万），按市价折合 约 0.2 元——连电费都不够。LLM 只能作为内部增值服务（网吧客服问答、游戏攻略助手）提升上座率，不能当独立收入项。

0.3 最高效方案：双线并行

这台机器真正的优势在于 OCR 走纯 CPU（RapidOCR + onnxruntime，不占 GPU，约 1–2GB 内存），而图像生成走 GPU——两者可同时跑，一台机器赚两份钱，且 31.2GB 内存完全够用（OCR 1–2GB + 图像模型 8–12GB + 系统 4GB ≈ 20GB 以内）。

· GPU 线：图像生成，约 36–90 元/小时
· CPU 线：OCR 识别，约 36–72 元/小时
· 合计理论峰值 72–162 元/小时，减机位机会成本（5–15 元）与电费（约 0.3 元）→ 毛利 57–147 元/小时
注意：这是「订单充足」下的理论峰值。没有订单，产能再高也是零——见 0.5。另外 OCR 产能取决于 CPU 核心数，本机核心数未取证，该数字待实测校准。

0.5 硬件天花板与风险

#约束影响处置
116GB 显存上限决定模型档位：图像可上生产档，视频只能低分辨率低量化，LLM 只能 27B Q3接受它，把业务压在「图像 + OCR」这条 16GB 的舒适区

4无订单 = 无收入上述毛利均为「订单充足」下的理论峰值先解决需求来源，再谈产能（见 0.6）

0.6 建议行动顺序

第一步（最高性价比）：部署 OCR 服务。已有现成组件 ocr/install.sh——纯 CPU、模型随 pip 包内置（零大文件下载，天然规避 COW 重启丢数据）、systemd 开机自启、独立 venv 不污染系统。这是唯一「不占 GPU + 不需下载大模型 + 立刻能产生收入」的项。
第二步：在同一批机器上叠加 GPU 图像生成，与 OCR 并行跑，实现双线收入。
第三步（可选）：H3 视频生成只用于自有内容运营，不对外接单；若确需商用视频，应换 24GB+ 显存机型而非在本机硬撑。

客户方向（本机最大差异化是「数据不出本地」）：
· 本地企业/机构（医院、律所、学校、政府）的文档数字化——数据合规是刚需，愿为私有化付溢价（云厂商 0.009–0.15 元/次，私有化可报 0.02–0.05 元/页）；
· 网吧自身客户的增值服务（AI 头像、游戏素材生成）——提升上座率而非直接创收；
· 不建议：零售 token、按秒卖视频、与大厂拼 LLM 价格。

一项值得评估的高价值补充：LoRA 微调服务。16GB 显存足够训练 SDXL 级 LoRA，单次交付可报价数百元，单位时间收益远高于按张出图。属服务型业务（需与客户沟通），未纳入上表产能计算。

四、四个隐藏分歧（比价时最容易算错的地方）

① 阶梯算法完全不同：腾讯是「阶梯到达」，百度是「分段累计」。
腾讯原文：后付费采取阶梯到达的计费方式，当月的接口总用量达到某个阶梯后，当月用量按该阶梯的单价进行计费。官方算例：20 万次 × 0.088 = 17600 元，整月统一按最低档单价。
百度算例：15 万次 = 2 万×0.100 + 3 万×0.095 + 5 万×0.080 + 5 万×0.070 = 12350 元，逐级累加。
同一个「月调用量阶梯」，两家算法不同，用量越大差额越大。

② 计费时间的口径：输出秒数 vs GPU 计算秒数。
按秒计费时，「秒」可能指输出视频时长，也可能指 GPU 实际运行时长，两者可差 2–3 倍。Replicate 定义更明确：公开模型只算 active 处理时间（setup 与 idle 免费），私有部署与 deployment 则连 setup、idle、active 全时计费。

③ 失败与并发的处理是隐性成本。
火山方舟、腾讯混元生图、MiniMax 均明示「生成失败不收费」；但腾讯 OCR 明确「部分失败错误码也计费」。并发上，腾讯混元生图默认仅 1 并发，要提并发须买 500 元/并发/天 或 10000 元/并发/月——这一项常常比图片本身还贵。腾讯还规定资源包耗尽或到期后不会自动转后付费，必须手动开通，否则调用直接失败。百度侧则需另购 QPS 叠加包（100–200 元/QPS/月）。

④ 牌价与主供应商报价能差一倍。
同一 1080p 文生视频：聚合器牌价 Seedance 2.0 $0.34/秒，主供应商 BytePlus 报 $0.31/秒；而 Wan 2.7 只要 $0.15/秒。8 秒 1080p 一条：Seedance $2.72 vs Wan $1.20。另外同一模型在不同平台用不同口径计价（火山按元/百万 token、fal.ai 按 $/1000 tokens、Runway 按 credits/秒），三种口径不可直接换算。

十三、调用方式的横向规律

① 鉴权只有三类，但决定要不要引 SDK。
· Bearer 直通（绝大多数）：阿里百炼、火山、智谱、MiniMax、千帆、可灵新版、OpenAI、Runway、Luma、Replicate
· 自定义头（非 Bearer，最容易写错）：Google x-goog-api-key、BFL x-key、fal.ai Authorization: Key、Pika X-API-Key、Azure Ocp-Apim-Subscription-Key
· 必须自实现签名（不引 SDK 就得手写）：腾讯 TC3-HMAC-SHA256（date 取 UTC，偏差 >5 分钟失败）、阿里 ACS3-HMAC-SHA256（x-acs-content-sha256 必须等于 body 的 SHA256）、百度 access_token（有效期 30 天需缓存）

② 异步三分法。
· 自建 task_id + 轮询（主流）：阿里百炼、火山视频、腾讯混元、智谱异步、Azure DI、可灵、千帆视频、MiniMax、Luma、Pika
· 平台原生 Operation 对象：Google Veo（operations.get()，看 done）、BFL（必须用返回的 polling_url）
· 提交即返全套 URL：fal.ai（status_url / response_url 一次给全）、Replicate（响应头 Location）

③ 结果 URL 有效期是集成设计的关键约束。
腾讯混元 1 小时 > BFL 10 分钟（最短）> 阿里/火山/千帆/可灵 24 小时 > Runway 24–48 小时 > 可灵内容 30 天后清理。务必在收到结果后立刻转存自己的存储，不要把厂商 URL 直接存进数据库当长期地址。

④ 返回形态决定客户端处理方式。
· base64 直返：OpenAI（b64_json）、Gemini 图像（inlineData）
· 二进制流：Stability（accept: image/* 直接是图像字节）
· URL：国内几乎全部、Runway、Luma、Replicate、fal.ai、Pika
· file_id 再换下载：MiniMax 旧版

⑤ 编码格式不能想当然。腾讯 OCR 与 OpenAI 图像编辑是 JSON + multipart 并存；百度 OCR 是 application/x-www-form-urlencoded 且要 urlencode；Stability 是 multipart 且需 files={"none": ''} 占位；智谱两个 OCR 端点一个 JSON 一个 multipart——混用直接 400。

⑥ 回调是省轮询的正路，但各家字段名不统一。可灵 callback_url、Luma callback_url、Replicate webhook + webhook_events_filter、fal.ai ?fal_webhook=、BFL webhook_url + webhook_secret。注意 fal.ai 回调里的 status 是 "OK"/"ERROR"，与 queue 状态 IN_QUEUE/COMPLETED 不同名。
