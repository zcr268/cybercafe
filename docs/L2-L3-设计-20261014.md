## 一 · 范围与边界

| 块 | 归谁 | 边界（切在哪） |
|---|---|---|
| **A · L2 独享** | L2 内部 | 不涉及 L3 如何执行、不涉及 KC 如何计费；L2 自成闭环：接单 → 排队 → 调度 → 适配 → 收结果 → 存产物 |
| **B · L3 收口** | L3 侧改造 | 只处理「公网暴露」这一维度：撤销对外隧道与直连，不改推理本身 |
| **C · L2 ↔ L3 链路** | 双方契约 | 两块之间唯一的通信定义：通道、报文、状态、失败语义 |

三者关系：**A 定义 L2 有什么能力，C 定义这些能力如何被 L3 消费，B 保证 C 只在私域内发生。**

本文件所有现状引用均来自代码实测（行号见审计文档），不引用设计文档当作已实现事实。

## 二 · A · L2 独享设计

### 2.1 服务骨架与存储

L2 本期**单点服务**（演进位见 R13），自带本地状态库，L1 离线时仍可接单与执行（R1 验收项）。

| 表/集合 | 关键字段 | 用途 |
|---|---|---|
| `devices` | `device_id`、`key_hash`、`hw_fingerprint`、`deployed`（组件+模型+档位）、`status`、`reserved`、`last_heartbeat` | 设备清单与模型池索引来源 |
| `tasks` | `task_id`、`component`、`model`、`params`、`state`、`device_id`、`created_at`、`started_at`、`finished_at`、`error`、`usage` | 任务全生命周期 |
| `queue` | `task_id`、`pool_key`、`enqueued_at` | 池满排队 |
| `artifacts` | `artifact_id`、`task_id`、`mime`、`bytes`、`path`、`expires_at` | 产物落盘与保留窗口 |
| `batches` | `batch_code`、`scope`、`local_count` | 本机房批次码（L1 持完整） |
| `cache_index` | `kind`(image/weight)、`key`、`path`、`size`、`built_at` | 两层缓存索引 |

现状对照：现有云端用集中式 KV（`cloud/src/index.js:335-338` 键约定 `device:/cmd:/log:/batch:/prov:`），只有设备与心跳维度，**无任务维度**（全仓无 `task_id`）。L2 需要的是关系型/可查询的任务状态，不是单槽 KV。

**L1 未上线期间**：L2 的身份注册与批次码先由**本地配置**承载（配置文件 + 本地签发），L1 上线后切换为下发通道（R8）；切换不改变 L2 对外协议。

### 2.2 统一任务 API（R2）

对外唯一契约，客户端与未来的 KC slave 用的是同一套（**不新增私有协议**）：

```text
POST /v1/tasks
  { "component": "ocr|t2i|t2v", "model": "<档位，可省>", "params": { ... }, "client_ref": "<可选外部编号>" }
→ 201 { "task_id": "t_xxx", "state": "queued", "poll_after": 1000 }

GET /v1/tasks/{task_id}
→ 200 { "task_id", "state": "queued|dispatching|running|success|failed|canceled",
        "progress": { "phase": "<步骤名>", "percent": 0-100 },
        "result": { "type": "text|image|video", "items": [ { "artifact_id", "mime", "bytes" } ], "meta": {} },
        "error": { "code": "...", "message": "..." },
        "usage": { "component", "model", "device_id", "queued_ms", "exec_ms", "input_size", "output_size" } }

POST /v1/tasks/{task_id}/cancel        # 可选，尽力而为
GET  /v1/tasks?state=&limit=           # 可选，运维用
```

**params 按能力定义（后端无关）**：

| component | params |
|---|---|
| `ocr` | `image`（artifact_id 或 base64）、`lang?`、`layout?` |
| `t2i` | `prompt`、`size?`、`n?`、`seed?` |
| `t2v` | `prompt`、`duration?`、`tier?`（fast/hd）、`seed?` |

**约定**：客户端永远不出现 `/sdcpp/v1/vid_gen`、`/prompt`、`/ocr` 这类引擎端点；换模型不改客户端（R5 验收项）。

**结果保留窗口**：默认 **24 小时**（L2 配置项，可按组件覆盖）；过期返回 `410 gone`，产物随之清理。

### 2.3 入口鉴权与限流（R3）

- **两类凭据严格分离**：对外 `site key`（客户端 / KC slave 用）与设备 `cck-` 密钥（仅 L3 自证身份）。
- 鉴权：`Authorization: Bearer <site_key>`；无凭据或错误凭据 → `401`。
- 限流：按 site key 维度，**QPS + 在途任务数**双限；超限 → `429` + `Retry-After`。
- 现状对照：现有 `deviceFromKey`（`cloud/src/index.js:205`）只做设备密钥校验，无对外 Key、无限流（审计 §CyberCafe 未实现项）。

### 2.4 队列与模型池调度（R4）

- **池定义**：`pool(component, model)` = `devices` 中 `deployed` 含该 `(component, model)` 且 `status=ready` 的机器集合。
- **选择**：池内按**在途任务数最少**；并列时用最近心跳的负载（`usage`）决胜；仍并列按 `last_heartbeat` 新者优先。
- **池满**：入 `queue`（FIFO，可配并发上限）；池空且存在可切模型机 → 交给 R12（P2）处理，本期先排队。
- **预留机**：`reserved=true` 的机器不参与切换、不被挤占（R12）。
- 现状对照：现在部署与调用**按 `device_id` 人工点名**（`cloud/src/index.js:655` 强制 `body.device_id`），无池、无在途计数、无排队。

### 2.5 组件适配层（R5）

适配器按**能力**定义（不绑模型），模型是可替换实现：

```text
Adapter { component, submit(device, task) → backend_ref,
          poll(device, backend_ref) → {state, progress?, result?, error?},
          cancel?(device, backend_ref) }
```

| 能力 | 当前模型/后端 | 提交 | 取结果 |
|---|---|---|---|
| OCR | RapidOCR / PaddleOCR | 组件 HTTP（`ocr/ocr.py:142` `POST /ocr`） | 同步返回 |
| 文生图 | OpenAI Images 兼容 | `POST /v1/images/generations` | 同步返回 |
| 文生视频 | **H3（sd-server）** | `POST /sdcpp/v1/vid_gen` | `jobs/{id}` 轮询（`cloud/public/index.html:807`） |

ComfyUI（`/prompt` + `/history`）作为**同能力的另一实现**未来接入，不改对外契约。

**错误归一**：`backend_unavailable | invalid_params | timeout | backend_error | capacity_full`，客户端只认这套码。

### 2.6 缓存两层（R7）

| 层 | 键 | 命中动作 | 未命中 |
|---|---|---|---|
| 镜像 | `fingerprint(GPU 型号 + 显存 + 驱动版本 + 内存 + CPU 组) + 组件版本` | 从 L2 本地镜像仓拉取，免构建 | 选一台构建并 push 入仓 |
| 权重 | `(组件, 模型, 版本)` | 从 L2 分发，免下载 | 回源一次（HF 等）后入库，后续命中 |

- L3 部署前先查 L2：`GET /v1/cache/lookup?kind=image|weight&key=...` → 返回可用源与大小。
- 现状对照：现有 `hw_fingerprint`（`agent/cybercafe-agent.py:457`）只用于设备身份去重，与镜像 tag 无关；权重每次直连 HF（`minimax-h3/install.sh:230,240`）、镜像走公共镜像站，**跨机重复下载**。

## 三 · B · L3 收口设计（R6）

### 3.1 现状与要撤销的东西

| 现状 | 位置 | 问题 |
|---|---|---|
| 每台机器自建 trycloudflare 隧道，把组件 API 直接出公网 | `agent/cybercafe-agent.py:1193,1203`、`cybercafe-deploy.py:680` | 违反「L3 永不做公网暴露」红线 |
| 管理 UI 直连隧道调用（`turl+/sdcpp/v1/vid_gen`、`turl+/ocr`、`turl+/v1/chat/completions`） | `cloud/public/index.html:796,807,847,1172` | 绕过 L2，无统一入口、无限流、无任务态 |
| 单机 nginx 鉴权网关暴露组件端口 | `cybercafe-deploy.py:647`（`proxy_pass 127.0.0.1:11434`） | 保留为内网入口可以，但不能对外 |

### 3.2 收口后的网络形态

```text
外部客户端 / KC slave ──→ L2 统一入口（唯一公网面）
                              │
                    网吧内网（私域 · 内网 HTTP）
                              │  L3 主动出站：心跳 / 取任务 / 回传
                              ▼
                        L3 工作机（不开任何公网端口、不建对外隧道）
```

- L3 **不开公网端口、不建对外隧道**；组件端口（OCR 8820 / H3 11435 / 引擎 11434）只在网吧内网可达。
- L2 ↔ L3 在网吧内网以 **HTTP** 互通（私域）：不建隧道、不依赖特殊容器网络；需要直连时同样走内网 HTTP。
- 现有单机 nginx 网关降级为内网入口，保留其鉴权能力。

### 3.3 身份与信任

- 设备密钥 `cck-`（`cloud/src/index.js:373,643`）**仅用于 L3 向 L2 自证身份**，不做对外鉴权（网吧内机器本身私有）。
- L2 可吊销设备：吊销后心跳被拒，在途任务重排。
- 私域 HTTP 上启用 TLS（内网可自签 + 固定指纹）或至少以设备密钥签名请求头，防内网嗅探与冒用。

### 3.4 迁移路径

1. **前置**：管理 UI 先具备经 L2 调用的路径（否则关隧道即功能缺口）。
2. **灰度**：新装机默认收口；存量机由 L2 下发指令停止隧道服务。
3. **验证**：确认外部无法直达 L3 端口（端口探测 + 隧道域名失效），且全部调用经 L2 成功。
4. **回退**：保留隧道开关作为过渡手段，但标注为临时态，不作为常态依赖。

## 四 · C · L2 ↔ L3 链路设计

### 4.1 链路模型（口径①）

**单向主动：L3 → L2 轮询**（沿用现有 agent 心跳取指令机制，天然穿 NAT、无需给 L3 开端口）。私域传输为**内网 HTTP**，凭据走请求头。

| 通道 | 方向 | 载体 |
|---|---|---|
| 注册 | L3 → L2 | `POST /v1/agent/register` |
| 心跳（顺带取指令） | L3 → L2 | `POST /v1/agent/heartbeat` |
| 进度上报 | L3 → L2 | `POST /v1/agent/progress` |
| 结果与产物上报 | L3 → L2 | `POST /v1/agent/result`、`POST /v1/agent/artifact` |
| 部署与管理指令 | L2 → L3（搭心跳回程） | heartbeat 响应体 `commands[]` |

L2 不对 L3 发起入站连接；所有 L2→L3 的动作都搭在心跳回程上。

### 4.2 注册与心跳

```text
POST /v1/agent/register { device_key, hw_fingerprint, batch_code?, capabilities:{components,models} }
→ { device_id, poll_after }

POST /v1/agent/heartbeat { device_id, status, usage{cpu,mem,gpu}, layers[], components[], inflight[] }
→ { commands: [ { cmd_id, kind, payload } ], poll_after }
```

- 现状可用：注册 `agent/cybercafe-agent.py:512`、心跳 `:586`（已带 `poll_after` 变速与 `usage/layers/components/busy`）。
- 心跳超时阈值 → L2 置 `offline`，其在途任务重排。

### 4.3 任务下发与确认

- L2 把任务转成指令放入该设备的**下发队列（多槽）**，随下一次心跳按序返回；单次心跳返回条数可配。
- 指令体：`{ task_id, component, model, params, backend_hint? }`
- L3 收到后先回 `accepted` 事件（进度通道），再执行；同 `task_id` 重复下发**只执行一次**（L3 侧去重）。
- **本期一并改造**：现有下发是 KV **单槽**控制指令 `cmd:<device_id>`（`cloud/src/index.js:285-287` 取出即删、`:667` 写入），并发任务会互相覆盖，必须改为多槽/队列。

### 4.4 进度与结果回传（含产物落盘，口径②）

```text
POST /v1/agent/progress { task_id, phase, percent? }
POST /v1/agent/result   { task_id, state, usage, result:{type, items:[{local_path|bytes}], meta} }
POST /v1/agent/artifact (multipart，分块) → { artifact_id }
```

- **产物落 L2 存储**：L3 把图片/视频上传到 L2，L2 落盘并返回 `artifact_id`；客户端经 `GET /v1/tasks/{id}` 拿到 `artifact_id` 后再从 L2 取。
- **L3 不留对外可访问的产物 URL**（收口要求）。
- **产物规格**：单文件上限 **2 GB**；按 **8 MB/块** 上传，支持断点续传；超限判 `failed`（`invalid_params`）并说明原因。
- **用量事实**（对应需求 I4）：`usage = { component, model, device_id, queued_ms, exec_ms, input_size, output_size }`——**L2 只给事实，费用计算归 KC**。

### 4.5 断连、重试与幂等

| 情形 | 处理 |
|---|---|
| L3 与 L2 断连 | L3 指数退避重试心跳；执行中的任务继续跑，结果暂存本地待连上再传 |
| L2 判定 L3 失联 | 超时阈值后置 `offline`；`dispatching/running` 的任务按策略重排或置 `failed` |
| 结果重复上报 | 幂等键 `task_id`（L2 侧去重，重复上报不重复计用量） |
| L2 重启 | 任务状态已持久化，恢复后按状态续跑（`running` 且设备在线则等待结果，否则重排） |
| 产物上传中断 | 分块续传；未完成则在保留窗口内重试 |

### 4.6 时序

**正常**：注册 → 心跳(空) → 客户端 `POST /v1/tasks` → L2 入队调度 → 心跳(带指令) → L3 `accepted` → 进度 → 结果 + 产物上传 → L2 落库 → 客户端轮询 `GET /v1/tasks/{id}` 取回。

**异常（执行中掉线）**：L3 执行中掉线 → 心跳超时 → L2 置 `offline` → 任务重排到池内另一台 → 原机恢复后上报的结果按 `task_id` 幂等丢弃或采纳（依状态机）。

## 五 · 状态与一致性

- **任务状态机**：`queued → dispatching → running → success | failed | canceled`；迁移只在 L2 落库。
- **事实来源**：L3 上报是执行事实，L2 是状态权威；两者冲突以 L2 状态机为准。
- **产物生命周期**：与任务绑定，随保留窗口过期清理；被引用期间不清理。
- **L1 离线 / 未上线**：不影响 L2 接单与执行（R1 验收项）；身份注册与批次码先由 **L2 本地配置**承载，L1 上线后切换为下发通道；聚合上报在恢复后补发。
